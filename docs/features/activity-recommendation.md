# 실행 이력과 추천

요구사항 ID: HIST-01~02, REC-01~06.

## 실행 이력과 추천

| ID | 기능 | 동작 기준과 완료 조건 | 범위 |
| --- | --- | --- | --- |
| HIST-01 | 실행 기록 | 명령 결과와 실제 앱 활동을 분리. 허용된 자비스 앱 실행·전환의 앱 ID·기기·발생 시각·출처·관측 수준을 기록하고 관련 명령에 연결. 요청 전달만으로 확인된 성공 활동을 만들지 않으며 중복 관측·전송은 같은 이벤트로 처리 | MVP |
| HIST-02 | 기록 관리 | 기록 조회·기간별 삭제·자비스 활동 수집 설정 제공. REC-05 도입 시 외부 활동 설정을 구분해 추가. 철회한 범위의 수집·업로드를 중단하고 대기 기록에도 적용. 수집 중지와 기존 기록 삭제는 별도 동작이며 명령 결과 보고는 수집 동의와 구분 | MVP |
| REC-01 | 연관 앱 추천 | 일정 시간 구간 안에 함께 실행한 앱의 빈도·순서를 분석. 최소 기록 조건 충족 시 추천 | MVP |
| REC-02 | 승인 실행 | 추천 ID·대상 앱·유효 시간을 표시. 서버가 유효한 승인을 확정한 뒤 생성한 명령만 실행. 추천 노출만으로 명령을 실행하지 않고 중복 승인을 방지 | MVP |
| REC-03 | 거절·닫기·만료 | 각각의 결과를 기록하고 실행하지 않음. 동일 추천에 재노출 제한 적용 | MVP |
| REC-04 | 추천 결과 기록 | 노출·승인·거절·닫기·만료와 대상 앱별 실제 실행 결과를 분리. recommendation_id로 승인에서 명령·실행 결과까지 연결하고 승인과 실행 성공을 동일시하지 않음 | MVP |
| REC-05 | 전체 앱 활동 분석 | 외부 활동 수집을 명시적으로 허용한 로그인 사용자에 대해 관측 가능한 앱 실행·포그라운드 전환을 수집. 외부 활동은 연결된 자비스 명령 없이 기록하며 철회·로그아웃 후 수집하지 않음. 앱 종료 관측과 MVP 포함 여부는 별도 결정 | 확장 |
| REC-06 | 고도화 추천·통계 | 시간대·반복 작업·일정·피드백을 활용하고 실제 기록에 근거한 추천 이유·통계 제공 | 확장 |

초기 추천은 규칙·통계 기반으로 구현할 수 있다. LLM은 설명을 돕더라도 빈도·비율을 임의 생성하지 않으며, 추천 실행 권한을 결정하지 않는다.

## 명령 결과와 앱 활동

최종 ERD에 따라 `COMMAND_RESULTS`는 명령의 실행 시도 결과, `APP_ACTIVITIES`는 관측된 앱 활동을 보관한다. 활동 정보 수집을 꺼도 사용자 명령의 실행 결과는 [명령 계약](../architecture/server-integration.md#명령-계획과-실행-결과)에 따라 보고한다. 실행 요청 전달(`dispatched`)은 실제 실행 확인(`confirmed`)과 구분해서 표시하며, 확인된 활동을 요구하는 추천 근거에 섞지 않는다.

활동 이벤트는 앱·사용자·기기, 발생 시각, 실행/활성화 등 유형, `source=jarvis/external/unknown`, 안정적인 `event_key`를 포함하고 자비스 명령에서 발생한 경우 `command_id`와 연결한다. 외부 활동은 명령 ID가 없다. 실행 명령이 이미 열린 앱을 앞으로 가져왔다면 실제 활동을 활성화로 기록한다. 최초로 관측한 외부 앱도 등록할 수 있도록 OS 앱 ID에서 서버 `device_app_id`로 연결하는 계약이 필요하며, 활동 수집을 위해 가짜 명령을 만들지 않는다.

명령 결과와 OS 관측에서 동일 활동을 중복 수집할 수 있으므로 상관관계·중복 판정 기준을 연동 전에 확정한다. 단순히 시각이 비슷하다는 이유만으로 외부 활동을 자비스 명령의 성공 증거로 삼지 않는다. 이벤트를 재전송할 때 새 `event_key`를 발급하지 않는다. 수집 범위는 자비스 프로세스가 실행 중인 동안 관측 가능한 앱 활동이며 창의 숨김·표시만으로 달라지지 않는 것을 기본안으로 한다. 실제 지원 OS·이벤트 범위는 검증 결과로 표시한다.

## 수집 설정과 삭제

| 계정 설정 | 기본값 | 제어 범위 |
| --- | --- | --- |
| `activity_collection_enabled` | ON | 자비스를 통해 발생한 앱 활동의 수집·저장. 가입 화면에 안내하고 설정에서 끌 수 있음 |
| `external_activity_collection_enabled` | OFF | 자비스 외부에서 발생한 앱 활동의 관측·수집·저장. 사용자의 명시적 활성화 필요 |
| `collection_revision` | 0 | 수집 설정 변경·기록 삭제마다 증가하며 오래된 대기 기록의 업로드 차단에 사용 |

기본값은 최종 ERD 6-1절을 따른다. 두 토글의 허용 조합, 특히 자비스 OFF/외부 ON의 의미는 7-1절과 일치하지 않아 [결정 목록](../delivery/validation.md#서버-erd-반영-후-결정-목록)에 남긴다. 외부 수집에 동의하지 않았다면 허용된 자비스 활동만 수집하고, 자비스 수집까지 꺼졌다면 그 활동도 수집하지 않는다. 외부 동의가 없다는 이유로 명령 실행 결과 보고를 끄거나, 명령 실행 동의를 외부 활동 수집 동의로 간주하지 않는다.

Main은 현재 인증된 사용자의 설정·정책 버전을 적용한다. 계정 설정을 아직 확인하지 못한 동안 기본값만으로 수집을 시작하지 않는다. 동의 철회는 로컬 수집·업로드부터 중단하고 서버 동기화 성공과 실패를 구분해 표시한다. 재연결 시 현재 정책과 삭제 범위를 먼저 확인하고, 철회·삭제 대상의 로컬 대기 기록이 다시 업로드되지 않게 폐기하거나 차단한다. 사용자 전환 후 이전 사용자의 대기 기록을 새 계정으로 보내지 않는다. 저장 위치는 [데이터와 보안](../architecture/data-security.md)을 따른다.

## 추천 승인

실행 결과 기록 → 서버 연관도 계산 → 유효한 추천 생성 → 현재 작업을 방해하지 않을 때 노출 → 명시적 승인 → 추천 상태를 한 번만 승인 상태로 전이 → 도구 실행 → 실제 결과 기록 순서로 처리한다. “응”은 현재 유효한 승인 대기 대상이 하나로 특정될 때만 승인으로 해석한다.

클라이언트의 승인 버튼은 서버에 해당 `recommendation_id`의 승인을 요청한다. 서버가 유효한 승인을 확정하고 명령을 생성하기 전에는 앱을 실행하지 않는다. 원래 사용자 요청에 추천이 함께 도착해도 추천 대상은 즉시 실행 목록에 넣지 않는다. 원래 요청이 끝난 뒤 승인한다면 별도의 유효한 요청/실행 수명을 만들고 닫힌 도구 호스트를 재사용하지 않는다.

추천에는 대상 앱 목록·표시 순서·서버가 정한 유효 기한을 연결한다. 최종 ERD의 초기 규칙(`rule-v1`)은 유효 시간 60초, PC당 유효한 대기 추천 1건이다. 클라이언트는 수신 시각부터 임의로 60초를 다시 세지 않고 서버 만료 시각을 적용한다. 재노출 제한과 분석 기준은 서버가 관리하며 카드의 승인·거절·닫기·만료를 보고한다. 필요한 만료·중복 방지 필드가 상세 테이블에서 빠진 부분은 [서버 확인 항목](../delivery/validation.md#서버-erd-반영-후-결정-목록)으로 남긴다.

승인한 여러 앱은 서버가 정한 실행 순서로 처리하고 결과를 앱별로 표시한다. 승인 요청 재전송으로 명령을 중복 생성하지 않으며, 거절·닫기·만료·로그아웃 이후 늦은 승인 응답으로 실행하지 않는다. 동일 추천의 승인·취소 경쟁과 중간 앱 실패의 후속 처리 기준은 명령 계약과 함께 확정한다.

서버는 사용자 요청 없이도 추천을 생성할 수 있다. 요청 응답에 붙는 추천과 별도 알림 조회로 도착하는 추천 모두 현재 사용자·기기·유효 기한을 검증하고 같은 승인 규칙을 적용한다. 독립 수신의 전송 방식은 API에서 확정하며, 시간대·일정 등 확장 추천(REC-06)을 이 계약만으로 MVP에 추가하지 않는다.
