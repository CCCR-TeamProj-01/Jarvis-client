# 계정 인증

요구사항 ID: AUTH-01~07. 자비스 계정의 로그인·회원가입·로그인 유지와 접근 제한의 원본 문서다. 상위 요구사항은 [BASE-01](../product/scope.md#공통-설정과-운영), 작업 이슈는 [#5](https://github.com/CCCR-TeamProj-01/Jarvis-client/issues/5)다.

## 범위와 화면

- 로그인 입력은 아이디·비밀번호다. 회원가입 입력은 아이디·아이디 중복 확인·비밀번호·비밀번호 재입력이다.
- 로그인 유지는 기본 동작이다. 앱을 다시 실행하면 저장된 인증 정보로 세션을 확인·복구한다. 비밀번호 저장 기능은 제공하지 않는다.
- 모든 주요 기능은 로그인한 사용자만 사용한다. 미로그인 또는 인증 확인 중에는 로그인·회원가입 화면 안에서 입력·진행·오류·재시도를 제공한다. 설정·대화·결과·추천 등 일반 화면은 열지 않는다.
- 로그인 전에는 카메라·마이크 수집, 호출어·손 인식, 제스처 제어, 앱·OS 실행과 계정 데이터 조회·전송을 시작하지 않는다. 이미 시작된 작업의 중지·정리와 앱 종료는 인증 없이 가능하다.
- 자비스 로그인과 Google Calendar·Outlook 연결은 별도 기능이다. 자비스 로그인 성공만으로 외부 캘린더 연결을 완료한 것으로 보지 않는다.

## 입력과 비동기 처리

`loginId`는 사용자가 입력하는 로그인 아이디이고 `userId`는 서버가 발급한 사용자 식별자다. 기록·기기 소유권에는 `userId`를 사용한다. 아이디 문자·길이·대소문자·공백 처리와 비밀번호 길이 규칙은 아래 합의 항목에 따라 클라이언트와 서버가 동일하게 검증한다. 비밀번호는 임의로 trim하거나 대소문자를 바꾸지 않는다.

- 중복 확인 상태는 미확인·확인 중·사용 가능·중복·오류다. 요청한 아이디와 요청 순서를 함께 추적한다. A 확인 후 B로 변경했다가 A로 돌아와도 이전 요청의 응답을 새 확인 결과로 사용하지 않는다.
- 중복 확인 실패를 사용 가능으로 처리하지 않는다. 가입 서버는 클라이언트의 확인 여부를 신뢰하지 않고 동시 가입을 포함해 아이디 유일성을 최종 보장한다.
- 비밀번호 재입력은 UI 폼 검증용이다. Main과 서버로 보내는 가입 입력에는 `loginId`·`password`만 포함한다. Main도 전달된 입력의 형식과 길이를 검증한다.
- 로그인·가입·복구 요청은 요청 식별자와 인증 세대를 유지한다. 로그아웃·계정 전환 이후 도착한 성공 응답이 다시 로그인시키거나 일반 화면을 열어서는 안 된다.
- 가입·로그인 요청 중 반복 제출을 막는다. 통신 실패는 잘못된 비밀번호나 아이디 중복과 구분하고 재시도 경로를 제공한다. 가입 응답이 불명확하면 무조건 자동 재가입하지 않고 로그인 또는 사용자 재시도를 안내한다.
- 가입·로그인 성공과 화면 전환, 폼 종료 시 비밀번호 입력을 비운다. 비밀번호·인증 비밀을 화면 전역 상태나 IPC 명령 기록에 보관하지 않는다.

## 인증 상태와 시작 흐름

인증 상태의 원본은 Main의 AuthManager다. 네트워크 연결 상태와 분리하고 UI에는 인증 비밀 없는 스냅샷만 전달한다.

| 상태 | 의미 | 화면·기능 |
| --- | --- | --- |
| checking | 앱 시작 시 저장 자격 증명 확인·복구 또는 유효성 재확인 중 | 인증 화면에 진행·재시도 표시, 주요 기능 차단 |
| signed_out | 사용할 자격 증명이 없거나 세션이 명시적으로 무효화됨 | 로그인·회원가입, 주요 기능 차단 |
| signed_in | 현재 인증 세대에서 확인한 사용자와 유효한 세션이 있음 | 사용자 화면과 기능을 권한·설정에 따라 허용 |

1. 앱 시작 시 인증 화면을 준비하고 주요 기능 시작을 보류한다.
2. 저장 자격 증명이 없으면 signed_out으로 전이한다. 있으면 checking에서 서버의 세션 검증·필요한 갱신을 수행한다. 저장값의 존재만으로 signed_in으로 전이하지 않는다.
3. 복구 성공 시 signed_in으로 전이하고 일반 화면·사용자 데이터·설정에 따른 기능을 활성화한다. 기기 연결은 확인한 사용자에 연결한다.
4. 만료·폐기 등 명시적인 무효 응답이면 저장 자격 증명을 제거하고 로그인 화면을 제공한다. 복구 중 일시적인 네트워크 장애이면 저장 자격 증명을 무조건 삭제하지 않고 인증 화면에서 재시도·다른 계정 로그인 경로를 제공한다. 검증을 마치기 전에는 주요 기능을 허용하지 않는다.
5. 이미 확인된 유효 세션에서의 단순 연결 단절은 로그아웃과 다르다. 유효한 인증 범위에서 로컬 제스처·중지 경로는 서버 응답 없이 동작한다. 인증 만료 후 갱신·검증이 필요하면 주요 기능을 차단하고 인증 화면에서 복구한다.

로그아웃·세션 무효화 시에는 인증 세대를 먼저 바꿔 새 실행을 막고, 대화·요청·제스처 세대를 무효화한 뒤 인식·입력·오디오·센서 사용권을 정리한다. 서버 세션 폐기는 가능한 범위에서 요청하지만 로컬 정리는 서버 응답을 기다리지 않는다. 저장 자격 증명 제거 실패는 숨기거나 로그아웃 완료로 안내하지 않으며 이 실행에서는 기능 차단을 유지하고 해결 경로를 제공한다.

계정 전환은 기존 세션 정리를 완료한 뒤 새 사용자 상태를 적용한다. 다른 사용자에게 이전 사용자의 기록·추천·일정·미완료 요청이 표시되거나 전송되지 않아야 한다. 재로그인은 취소·만료된 작업이나 이전 계정의 명령을 자동 재실행시키지 않는다. 센서·제스처의 재활성화는 현재 사용자의 설정과 유효한 새 요청에 따른다.

## 클라이언트 계약과 구조

F-008에서 아래 데이터·API·Main 포트 계약을 구현했다. F-009에서 로그인/회원가입 화면 틀과 일반 UI IPC를 연결했다. AuthManager·입력/제출·인증 IPC 핸들러·서버/보호 저장소 구현은 후속 작업이다. 현재 Preload는 InteractionUiApi만 노출하며 auth 영역은 아직 노출하지 않는다.

| 위치 | 책임 | 상태 |
| --- | --- | --- |
| `src/shared/contracts/auth.ts` | 로그인·가입 입력, 아이디 사용 가능 결과, 공개 사용자 정보, 인증 스냅샷·이벤트·로그인 유지 결과 | 계약 구현 |
| `src/shared/ipc/auth-api.ts` | UI 전용 인증 API와 응답 스키마. 로그인·가입·중복 확인·복구 재시도·로그아웃·상태 조회·구독 | 계약 구현 |
| `src/main/auth/ports.ts` | 인증 서버 어댑터와 보호 자격 증명 저장소의 Main 내부 포트 | 계약 구현 |
| `src/main/auth/auth-manager.ts` | 인증 상태·세대·유지·복구·만료·로그아웃과 기능 차단 조정 | 후속 구현 |
| `src/renderer/ui/features/auth/` | 로그인·회원가입 입력/제출, 비밀번호 재입력 검증, 요청별 진행·오류 표시. 현재 화면 틀은 UI main.tsx에 위치 | 후속 구현 |

UI 공개 API 계약은 `UiApi.auth` 아래 `checkLoginId`, `signUp`, `signIn`, `restore`, `signOut`, `getSnapshot`, `subscribe`로 구성한다. `restore`는 통신 장애 후 Main에 보관된 자격 증명으로 복구를 재시도하며 UI에서 토큰을 받지 않는다. 실제 핸들러 구현 시 입력값은 제한된 Preload API를 거쳐 Main에 전달하고 인증 요청은 Main이 HTTPS로 수행한다. `AuthGatewayPort`는 인증 서버 작업을, `CredentialStorePort`는 자격 증명 읽기·저장·제거를 추상화한다. 토큰 형식과 자격 증명 객체는 Main 내부 계약이다.

`AuthSnapshot`에는 phase·현재 인증 세대·확인된 사용자만 포함하고 비밀번호·세션 토큰은 넣지 않는다. checking·signed_out에서는 user가 null이고 signed_in에서는 공개 사용자가 필수다. 로그인·가입·복구의 요청 중 표시는 인증 완료 상태와 구분한다. `ClientSnapshot.auth`로 상태를 연결하고 screen에 login·signup을 추가했다. 미인증 스냅샷에서 일반 화면을 보고하면 스키마 검증이 실패한다. 이 데이터 검증과 별도로 실제 Main 실행 경로의 인증 확인을 구현해야 한다.

인증 요청은 requestId·generation과 input을 담는다. 비밀번호 없는 복구·로그아웃 요청은 requestId·generation만 사용한다. 요청 식별자와 세대의 동시 일치는 `isCurrentAuthRequest`로 검사할 수 있다. UI 화면 전환은 `auth.open` 명령으로 요청한다. Main이 현재 인증 세대·발신자를 검증하는 책임은 그대로 유지한다.

결과는 기존 `Result<T>` 형식을 사용한다. `ClientError`에 authentication_required·invalid_credentials·login_id_taken·session_expired·rate_limited·credential_unavailable을 추가했다. 로그인·복구 성공 결과는 signed_in 스냅샷과 persistence를 분리한다. persistence가 unavailable이면 credential_unavailable 오류가 필수이며 로그인 유지 성공으로 표시하지 않는다.

개발용 인증 대역은 같은 포트 뒤에 두고 개발 환경에서 명시적으로 선택한다. 운영 빌드가 대역으로 인증을 통과해서는 안 된다. 실제 인증 어댑터가 없어도 폼·복구·만료·기능 차단·계정 전환을 검증할 수 있어야 한다.

## 저장·서버 연동과 합의 항목

비밀번호·토큰 저장과 로그 경계는 [데이터와 보안](../architecture/data-security.md#인증-정보와-계정-격리)을, 인증 연산의 서버 책임은 [서버 연동](../architecture/server-integration.md#계정-인증-계약)을 따른다. 로그인 유지 저장에 실패하면 이를 알리고 현재 실행의 로그인과 다음 실행의 복구 가능 여부를 구분한다. 평문 저장으로 대체하지 않는다.

현재 입력 스키마는 아이디가 공백만으로 구성되지 않는지와 비밀번호가 비어 있지 않은지만 검사하며 입력을 정규화하지 않는다. 다음 항목은 구체적인 입력 정책을 적용하는 폼·Main 검증과 실제 서버 어댑터 구현 전에 합의한다.

- 아이디 허용 문자·최소/최대 길이·대소문자 구분·정규화와 비밀번호 최소/최대 길이. 중복 판정과 가입 저장에 같은 규칙을 사용한다.
- 인증 엔드포인트·오류 형식·로그인 유지용 자격 증명·세션 검증/갱신·만료 시간·기기 연결과 폐기 방식.

기능 완료 검증은 [배포와 검증](../delivery/validation.md#인증-검증)을 따른다.
